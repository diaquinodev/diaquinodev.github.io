Casos

Seis casos, todos com testes e CI.

Estudos de caso curtos de projetos de portfólio, com dados fictícios ou sintéticos. Cada um mostra o contexto, o problema, a abordagem e o que dá para verificar no repositório, inclusive os limites.

Nenhum caso aqui é trabalho feito para cliente real, e nenhum afirma ganho financeiro ou de tempo medido em operação. O que está escrito como resultado é o que o repositório mostra: testes, CI e execução com dados fictícios ou sintéticos. A experiência profissional anterior está resumida em Sobre, sem dados nem detalhes de empresas.

Caso em destaque 01

Conferir o repasse do gateway contra o contrato

auditor-de-repasses

Projeto de portfólio · dados fictícios

Contexto
Cenário fictício: um seller de e-commerce que recebe repasses de um payment gateway, com descontos de MDR, antecipação, estornos e prazos de pagamento.
Problema
Conferir linha a linha contra o contrato é manual e lento. Cobrança indevida vira perda silenciosa, e a divergência a favor passa despercebida até o parceiro cobrar de volta.
Abordagem
Um agente de IA lê o contrato em PDF e uma pessoa confere as regras extraídas. A conciliação em si é código determinístico, com dinheiro em Decimal. As divergências são agrupadas pelo padrão do erro, e cada grupo recebe uma análise (causa provável, cláusula, minuta de contestação) que uma pessoa aprova. A IA não escreve valores: uma checagem acusa qualquer número monetário que não veio do motor. A saída é um relatório em Excel.
Stack
  • Python
  • pydantic
  • Streamlit
  • pytest
  • ruff
  • mypy
  • GitHub Actions
  • Gemini (opcional, há modo demo)
Resultado verificável
Na demonstração, com 248 transações fictícias: 80 divergências em 5 grupos, e 5 chamadas de IA em vez de 80. O eval com divergências plantadas (20 cenários, modo demo) achou todas as plantadas, sem alarme falso. 66 testes automatizados, com lint e tipos checados no CI.
conferido

Contagem de testes e último CI na branch principal conferidos no repositório em 02/10/2026. Contei as funções de teste e vi o CI passar; não reexecutei a suíte.

Limites
O eval em modo demo mede o código (motor, agrupador, checagens), não a IA; a medição com o Gemini é um próximo passo do README. Um parceiro e um formato de CSV; sem chargeback.

Caso em destaque 02

Esteira diária de extratos de vários bancos

conciliacao-bancaria-automacao

Projeto de portfólio · dados sintéticos, sem bancos reais

Contexto
Cenário hipotético: uma área financeira com 8 contas em bancos diferentes, cada extrato num formato e num horário. Os bancos e os dados são sintéticos; não há integração com nenhuma instituição real.
Problema
Extratos em formatos distintos, cargas repetidas que duplicam lançamentos e divergências que só aparecem no fechamento.
Abordagem
Esteira de ponta a ponta: extração (retentativa com backoff e circuit breaker por banco), ETL em Power Query, persistência em SQL com chave idempotente (SHA-256 e UNIQUE), regras de divergência (duplicata, outlier e teto de alçada), trilha de auditoria e painel HTML com filtros.
Stack
  • Python
  • pandas
  • SQL (T-SQL e SQLite)
  • Power Query (M)
  • Chart.js
  • GitHub Actions
Resultado verificável
30 testes automatizados, rodando no CI em Python 3.12 e 3.13. Reprocessar o lote de referência (216 transações sintéticas) não duplica nada: as já gravadas são ignoradas. O projeto não afirma ganho financeiro nem de tempo.
conferido

Contagem de testes e último CI na branch principal conferidos no repositório em 02/10/2026. Contei as funções de teste e vi o CI passar; não reexecutei a suíte.

Limites
Roda em modo demo (SQLite; o T-SQL é o modelo-alvo). A chave idempotente é por conteúdo: duas compras idênticas no mesmo segundo seriam tratadas como uma. A extração é sequencial.
Ver o repositório no GitHub (conciliacao-bancaria-automacao)

Caso em destaque 03

Preço certo por canal, sem prejuízo escondido

dashboard-precificacao

Projeto de portfólio · dados de exemplo fictícios

Contexto
Quem vende o mesmo produto em vários marketplaces (Shopee, Mercado Livre, TikTok Shop e Shein) precisa saber por quanto anunciar em cada canal. É a reescrita, com testes, de uma ferramenta que fiz antes para consultorias de e-commerce. Roda no navegador, sem login.
Problema
A taxa muda conforme a faixa de preço, e o preço depende da taxa. Na planilha, o erro comum é usar a taxa da faixa errada. Exemplo do README: a fórmula simples usa a taxa da faixa errada e, nesse preço, o marketplace cobra mais, então cada venda dá prejuízo; o preço certo fica numa faixa acima.
Abordagem
Um motor de cálculo puro (sem DOM) resolve o preço em cada faixa de taxa e fica com o menor preço consistente; se nenhuma faixa serve, responde “margem inatingível” em vez de um número absurdo. A importação de catálogo (CSV ou Google Sheets) relata cada linha ignorada e o motivo. As taxas são editáveis, com vigência e fonte.
Stack
  • JavaScript (JSDoc e TypeScript strict)
  • Node.js
  • ESLint
  • Prettier
  • GitHub Actions
Resultado verificável
32 testes de unidade e 13 de ponta a ponta no Chrome (números do README; não os reexecutei). Cinco bugs da versão anterior estão cobertos por teste. A demonstração pública respondeu normalmente em 02/10/2026.
Limites
As taxas padrão vêm de fontes secundárias (consultadas em 10/2026) e precisam ser conferidas no painel do vendedor. A comissão por categoria não está modelada.

Caso 04

Estoque no ERP com alertas de ruptura

wms-bling

Projeto de portfólio · sem dados de operação no repositório

Contexto
Loja de moda omnichannel que vende no site próprio e em marketplaces, com o estoque controlado no ERP Bling. O repositório não traz dados de operação e, para rodar, exige credenciais próprias do Bling.
Problema
Produtos zeravam sem ninguém perceber e o anúncio continuava ativo; a conferência de pedidos era manual, com erro de item e de baixa; as planilhas de estoque para o hub de marketplaces eram montadas à mão.
Abordagem
Servidor Node.js que integra a API v3 do Bling (OAuth 2.0 com renovação automática do token e cache de 30 minutos para respeitar limites), três painéis web (estoque, conferência de pedidos, entrada e saída), exportação de ZIP de estoque para o hub e um robô horário que avisa produtos zerados ou com estoque baixo em um grupo de WhatsApp, em lotes.
Stack
  • Node.js
  • Express
  • Bling API v3
  • OAuth 2.0
  • node-cron
  • whatsapp-web.js
  • GitHub Actions
Resultado verificável
7 testes (node --test) cobrem as regras puras do robô de alertas e rodam sem Bling nem WhatsApp; CI em Node 20 e 22. O README não mede o efeito na operação: não há número de resultado.
conferido

Contagem de testes e último CI na branch principal conferidos no repositório em 02/10/2026. Contei as funções de teste e vi o CI passar; não reexecutei a suíte.

Limites
O cache é em memória (sem histórico). Pensado para rede interna, sem autenticação nos painéis. Os testes cobrem só as regras do robô; a integração com o Bling e os painéis não têm teste automatizado. O envio usa a biblioteca não oficial whatsapp-web.js.

Caso 05

Radar de mercado e agentes de IA para anúncios

radar-marketplace

Projeto de portfólio · sem dados de clientes no repositório

Contexto
Loja de moda que vende no Mercado Livre, onde cada produto novo exigia horas de trabalho manual: pesquisar a concorrência, precificar, criar o anúncio e acompanhar a saúde dele.
Problema
Pesquisar preço e volume da concorrência, precificar depois das taxas e promoções, montar título, ficha técnica e fotos, e corrigir o que o marketplace penaliza: tudo à mão, para cada produto.
Abordagem
Dashboard Streamlit que extrai até 500 anúncios de uma busca e consolida preço, desconto e vendas com pandas; cálculo de preço mínimo, preço-alvo e kit já descontadas as taxas; análise SWOT por IA; agente que lê fotos da peça e devolve a ficha técnica em JSON validado (Pydantic); auditor de anúncio; robô Playwright de publicação; integração OAuth com a API do Mercado Livre.
Stack
  • Python
  • pandas
  • Streamlit
  • Playwright
  • Pydantic
  • Gemini
  • API Mercado Livre
Resultado verificável
25 testes pytest (número do perfil no GitHub; não os reexecutei) cobrem precificação, limpeza de vendas, o parser do scraper (com HTML simulado) e o schema da ficha técnica; rodam sem rede e sem chave, e no CI. Agentes, integrações e RPA não têm teste, porque dependem de APIs externas, como o README já avisa.
Limites
A coleta de dados públicos precisa respeitar os termos de uso do marketplace; para uso contínuo, o README recomenda a API oficial.
Ver o repositório no GitHub (radar-marketplace)

Caso complementar 06

Estúdio de fotos de produto com IA e cota de créditos

estudio-fotos-marketplace

Projeto de portfólio · marca de exemplo fictícia · caso complementar

Contexto
Ferramenta interna para uma empresa gerar fotos de produto para marketplaces, fiéis à peça de referência, sem precisar escrever prompts. A marca “Ateliê Aurora” do exemplo é fictícia. O README traz um relato do autor sobre o problema de origem, que não é verificável pelo código.
Problema
Segundo o relato do autor no README (não verificável): gerar imagens para e-commerce consumia horas dos colaboradores, com resultado inconsistente.
Abordagem
App Next.js com login Supabase, assistente em 3 etapas e prompt montado no servidor a partir de parâmetros tipados, com geração pelo Gemini. A cota de créditos usa reserva atômica no Postgres, com confirmação ou estorno, e há limite de requisições por minuto. A galeria usa armazenamento privado.
Stack
  • Next.js
  • React
  • TypeScript
  • Supabase (Auth, Postgres, Storage)
  • Gemini
  • Vitest
  • GitHub Actions
Resultado verificável
61 testes (número do perfil no GitHub; não os reexecutei; 11 exigem PostgreSQL e rodam no CI), incluindo o débito de créditos testado em Postgres real com 12 requisições concorrentes disputando 3 créditos.
Limites
A chamada real ao Gemini e o fluxo completo no navegador não foram exercitados no repositório. A fidelidade à peça é só instrução de prompt, sem verificação automática. As migrações não foram aplicadas num projeto Supabase real. A licença não está definida.
Ver o repositório no GitHub (estudio-fotos-marketplace)
